# Архитектура

[English](../en/architecture.md) · **Русский** · [Вся документация](README.md)

```
 агент / рой ──MCP stdio──► dah-bridge ──┐
 хаб DreamTeam ◄──continue── dah-waker ──┤
 боты (dah bots run) ────────────────────┼─HTTP /v1─► dah serve (server/app.py)
 ваша программа ─────────────────────────┘                │
                                                GameRegistry ─► Game (game.py) ─► engine (чистые правила)
                                                                   │
                                                  games/<id>/: config.json, keys.json, journal.jsonl, private/
```

- Всё, что делает игрок, идёт через HTTP API. Боты пользуются тем же API, что и агенты, без поблажек.
- Движок — чистая библиотека: на входе правила, на выходе состояние; без часов, сети и файлов, кроме чтения паков.
- `Game` добавляет то, что зависит от времени и мест: фазы, дедлайны, ready, книги приказов, сообщения, журнал.
- Сервер — тонкий слой над `Game`: аутентификация, JSON туда и обратно, событие `call` на каждый запрос.

## Движок

- `build_ruleset(pack_dirs, scenario)` загружает и проверяет паки и возвращает `Ruleset`: все сущности с полными
  ID, карту, сценарий, итоговые характеристики (с правками сценария и модификаторами каждой фракции) и `hash`.
- `new_game_state(ruleset, seats, seed)` раздаёт старты и возвращает состояние первого хода.
- `submit_orders`, `cancel_order`, `amend_order` принимают книгу приказов места и возвращают новую, с причиной
  каждого отказа. Входные данные они не меняют.
- `resolve(state, orders_by_seat, ruleset, seed)` возвращает новое состояние и `TurnReport`: все события, часть,
  которую видит каждое место, публичную часть (смены владельцев, выбывания, счёт, итог) и статистику простоя.
- `view_state` и `render_state_text` применяют туман войны; `rules_text` пишет правила по набору правил.

## Game

`Game` (в `game.py`) оборачивает движок для одной партии:

- цикл фаз `negotiation_1 → actions → negotiation_2 → resolution → negotiation_1` следующего хода, в конце —
  `game_over`;
- внедряемые часы: `tick()` закрывает фазу, у которой прошёл дедлайн, поэтому тесты идут без ожидания;
- книга приказов каждого места на текущий ход, флаги ready и проверка `confirm_hash`;
- лимиты сообщений и обёртка `untrusted`;
- `phase_seq` и `wait_phase`, который будит ждущие запросы при каждой смене фазы.

Каждое изменение пишется в журнал, а живой снимок — в `private/runtime.json`. По нему `Game.load` восстанавливает
партию после перезапуска сервера.

## Каталог партии

`dah game create` создаёт `games/<id>/`:

| Путь | Содержимое |
|---|---|
| `config.json` | конфиг партии без ключей: ID, seed, сценарий, каталоги паков, места, лимиты |
| `keys.json` | `{sha256(ключ): место}` |
| `journal.jsonl` | журнал, одно событие на строку |
| `private/runtime.json` | живой снимок: состояние, книги приказов, флаги ready, время фазы |
| `private/states/turn_<N>.json` | состояние в начале хода N |
| `private/orders/turn_<N>.json` | книги приказов, рассчитанные в конце хода N |
| `private/reports/turn_<N>.json` | полный отчёт хода N |
| `private/messages.jsonl` | полные тексты сообщений |
| `private/bot_keys.json` | ключи мест-ботов для `dah bots run` |

Каталог `private/` сервер игрокам никогда не отдаёт. В журнале — размеры сообщений, а не тексты.

## Журнал

`journal.jsonl` только дописывается; каждая строка — `{seq, ts, type, ...}`. Типы событий:

| Тип | Основные поля |
|---|---|
| `game_created` | конфиг (без ключей), `ruleset_hash`, `seed`, `rules_chars` |
| `seat_info` | место, вид, declared, `dreamteam_session_id`; при более поздней привязке ещё `update: true`, `previous`, `source` (`cli` или `waker`) |
| `phase_open` / `phase_close` | ход, фаза, дедлайн / причина `all_ready` или `deadline`, `not_ready` (живые места, не нажавшие ready) |
| `recon` | ход (пустой разведсрез) |
| `call` | место, маршрут, `req_chars`, `resp_chars`, `ms`, статус, ход, фаза, `host` у служебных вызовов |
| `first_call_in_phase` | место, ход, фаза |
| `orders_validated` / `orders_submitted` | место, принятые или их число, отклонённые с причинами, `orders_hash`, фаза |
| `order_edit` / `order_edit_p2` | место, операция, ID приказа, цена в ОК (в П2 — и для новых приказов) |
| `ready` / `unready` / `ready_cleared` | место, ход, фаза |
| `message` | от кого, кому, число символов, фаза |
| `turn_resolved` | ход, `state_hash`, счёт, простаивающие ресурсы и юниты, `autopilot` (места, у которых к расчёту не было приказов) |
| `spend_report` | место, `spent_usd`, источник, токены, `for_turn`/`for_phase` (за какую фазу цифра; `null` у отправной точки), `at_turn`/`at_phase` (когда получена), `turn`/`phase` (пара «за», иначе пара «когда») |
| `telemetry` | место, вид, detail |
| `game_over` | победители, причина (`last_standing` или `turn_limit`), счёт, ход |

Сбой посреди записи оставляет не больше одной оборванной строки: при чтении она пропускается, а запись
продолжается со следующей строки.

## Детерминизм

- Вся случайность берётся из `rng.stream(seed, turn, system, entity)`: `random.Random` с зерном из sha256 строки
  `"{seed}|{turn}|{system}|{entity}"`. Глобальной случайности нет. Старты раздаются из одного потока, у каждого
  боя свой поток — по провинции или ребру.
- У `estimate` фиксированное зерно, поэтому на один вопрос всегда один ответ.
- Контент обрабатывается в порядке полных ID, а не файлов.
- Боты детерминированы от зерна места (sha256 от ID партии и места).

Поэтому одни и те же правила, зерно и приказы всегда дают одну и ту же партию.

## state_hash и повтор

`state_hash` — sha256 канонического JSON состояния (ключи отсортированы, без пробелов) без счётчиков ID приказов
по местам. Журнал записывает его в каждом событии `turn_resolved`.

`dah replay <id>`:

1. пересобирает набор правил по конфигу и сверяет его хэш с `ruleset_hash` из журнала;
2. создаёт начальное состояние из зерна;
3. рассчитывает каждый ход по приказам, сохранённым в `private/orders/`;
4. сверяет `state_hash` каждого хода, победителей и итоговый счёт с журналом.

Расхождение значит, что изменились правила или контент либо расчёт недетерминирован. Команда завершается с кодом 1.

## Отчёт

`dah report <id>` читает только журнал. Он раскладывает время по местам и фазам (до первого вызова, до первой
принятой подачи, до ready), считает вызовы и символы (служебные отдельно), подачи (и по видам фаз: П1 / Д / П2),
правки и отклонения, простаивающие ресурсы и юниты, ходы, в которых место не подало приказов, фазы, закрытые по
таймеру без ready места, счёт по ходам, деньги по ходам и фазам из `spend_report` (по полям «за»), деньги и время
во время партии и после game_over отдельно (`spent_in_game_usd`, `spent_after_game_usd`, `in_game_s`,
`after_game_s`) и телеметрию waker. Ради этого срез и сделан: замерить, сколько денег и времени стоит ход рою DreamTeam и одиночному агенту.

## Сервер, мост, waker, боты

- `server/registry.py` держит загруженные партии и сопоставляет хэши ключей с (партией, местом). Неизвестный ключ
  правильного вида запускает пересмотр каталога партий, не чаще раза в 2 секунды.
- `bridge/` — stdio MCP-сервер (пакет `mcp`). Каждый инструмент — один HTTP-вызов; ответ — `text` сервера или
  компактный JSON. Ключ вычищается из любого текста, который покидает процесс.
- `waker/` ждёт фаз через long-poll `/v1/wait_phase` и вызывает у DreamTeam `/api/v1/sessions/{id}/continue` и
  `/api/v1/sessions/{id}` (после game_over с `--stop-on-game-over` — ещё `/api/v1/sessions/{id}/stop`), а после
  game_over продолжает сообщать расход сессии, пока она не остановится или не затихнет.
- `bots/` используют общий цикл (`base.py`): дождаться фазы, прочитать состояние в JSON, действовать, нажать ready.
